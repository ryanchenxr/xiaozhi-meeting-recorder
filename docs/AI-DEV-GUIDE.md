# 用 ESP32-S3 做一台"AI 会议录音台"：给 AI 的避坑开发指南

> **怎么用这份文档：** 把它完整丢给你的 AI 编程助手（Claude Code / Codex / Cursor 等），再说一句"按这份指南，在我的板子上实现会议录音台"。
> 文档是写给 AI 看的：先讲目标和架构，再列出我们真实踩过的坑（症状 → 根因 → 解法 → 怎么验证），最后给出关键参数和测试方法。
> 作者：陈虾仁（用 Claude Code + Claude Opus 5.5 完成），2026-10。基于开源项目 [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)（MIT）。
> 参考实现：本仓库的 `firmware/`（固件）、`receiver/`（接收端）、`firmware-tests/`（单元测试与传输模拟）。

---

## 0. 给 AI 的工作守则（请先读）

1. **先算账，再改代码。** 任何"录着录着就断"的问题，先算：每秒产生多少数据、链路每秒能送出多少、每次请求的往返时间是多少。我们最早卡住好几轮，就是因为一直在调参数，而没有算这笔账。
2. **"成功一次"不等于成功。** 每次录音都要做端到端对账：样本数、包数、字节数、SHA-256 都一致，才算成功。我们有一次 10 分钟录满、数据全到，最后差 0.01 秒，就是靠对账抓出来的。
3. **一次只改一类东西，每次都要上真机验证。** 模型和单元测试能排除大部分错误，但 Wi-Fi、内存、芯片缓存这类问题只有真机能暴露。
4. **需要人动手（刷机、插拔、说话）时，给出逐条编号的具体步骤**，并说明现在能不能拔线、关机。
5. **凭据永远不进日志、不进对话、不进仓库**（设备密钥、服务账号、API Key）。
6. **不要静默失败。** 录音不完整就明确报错，并且不提交；宁可失败，也不交一份残缺的会议记录。

## 1. 目标效果

- 会议桌上放一块小板子，说"你好小智，开始记录会议"，开始录音；
- 说"你好小智"，然后第一句说"结束会议记录"（或者按一下按键），结束录音；
- 录音自动交给转写和纪要服务（我们用的是"得到大脑"），几分钟后板子屏幕弹出二维码，同事扫码就能看纪要；
- 支持最长 **60 分钟**，家里和公司都能用，不用改设置。

我们最终实测：60 分钟完整录音（中途网络失败 34 次，全部自动恢复），交给服务后 67 秒出完整文字、约 3 分钟出纪要，板子弹二维码，手机扫码查看。

## 2. 硬件

| 项目 | 我们用的 | 最低建议 |
|---|---|---|
| 主控 | ESP32-S3（N16R8：16 MB Flash + 8 MB Octal PSRAM） | ESP32-S3，**PSRAM ≥ 8 MB** |
| 麦克风 | ES7210 采集芯片 | 任意能采 16 kHz 的麦克风 |
| 屏幕 | 320×240 SPI LCD（ST7789） | 能显示二维码即可 |
| 按键 | BOOT + 音量加减 | 至少 1 个按键 |
| 电池 | 有 | 可选 |
| 板型 | 征辰 AI Camera（xiaozhi 固件中的 `zhengchen-cam`） | 任何 xiaozhi 支持的 S3 板子 |

**为什么 PSRAM 很关键：** 网络卡顿时，录音要先存在板子上；我们用了 3 MB PSRAM 做缓冲，能扛约 13 分钟的网络停顿。芯片内部那块几百 KB 的 SRAM 才是真正紧张的资源（见第 4 节）。

## 3. 总体架构

```
[板子] 边录边压缩（Opus）
   │  局域网 HTTP，小块连续上传，可断点重试
   ▼
[接收端：局域网里的一台常开电脑]
   │  校验完整性 → 解码成 WAV → 大于 32 MiB 时转成 m4a
   ▼
[转写 / 纪要服务]（我们用得到大脑）
   │  返回笔记 → 生成不含原音的分享链接
   ▼
[接收端] 把链接做成二维码 → 板子轮询状态 → 屏幕显示二维码
```

**为什么不让板子直接上传到云端：**
- 云端一般要 HTTPS，TLS 握手要占用几十 KB 芯片内部内存，而录音时内部内存只剩十几 KB；
- 我们用的转写服务没有公开的"上传音频"接口（见坑 21）；
- 局域网内传输稳定、便宜，接收端还能做存档和校验。

**为什么在板子上压缩：** 16 kHz 单声道 PCM 每秒 32 KB，家庭 Wi-Fi 上行偶尔会掉到每秒 8～9 KB。用 Opus 压缩后每秒约 4 KB（实测平均约 3.2～3.8 KB），只有原来的 1/8。

## 4. 坑清单（核心）

每条格式：**症状 → 根因 → 解法 → 怎么验证**。

### 坑 1：录几十秒到几分钟就断（"队列满了"）
- **症状**：录音很快中断，板子报"队列满"。
- **根因**：每 100 ms 发一小包（3.2 KB），**发一包、等确认、再发下一包**。家庭 Wi-Fi 上一次请求往返要 200～600 ms，送出去的速度永远赶不上录音的速度。我们一开始反复调省电模式、Nagle、连接复用，都没解决。**问题不在带宽，在往返次数。**
- **解法**：批量发送。每次把已经攒下的数据全部带上（我们设定每块至少 8 个 Opus 包、约 0.48 秒，最多 16 KB），慢的请求之后自然跟着一个更大的块。
- **验证**：日志里记录每次请求的耗时和队列深度；正常时队列应该一直接近 0。

### 坑 2：链路突然变慢，PCM 撑不住
- **症状**：10 分钟测试在第 22 秒中断。
- **根因**：家庭 Wi-Fi 上行从每秒 40～80 KB 掉到每秒 8～9 KB，低于 PCM 需要的每秒 32 KB。
- **解法**：在板子上实时压缩成 Opus：16 kHz 单声道，60 ms 一包，32 kbit/s VBR，complexity 0，**关闭 DTX**（保证每 60 ms 一定有一包，方便对账）。传输格式是 `[2 字节小端长度][Opus 包]` 依次拼接。
- **验证**：接收端逐包解码，每包必须恰好 960 个样本。

### 坑 3：Opus 编码任务栈溢出，一开始就重启
- **症状**：一按开始，板子立刻重启（stack overflow）。
- **根因**：VOIP 模式会启用 SILK 编码器，24 KB 的栈不够用。
- **解法**：编码任务栈给到 64 KB（实测峰值约 28 KB）。栈放在哪里见坑 8。
- **验证**：会话结束时打印栈的高水位（剩余量）。

### 坑 4：录满了、数据全到了，最后还是"失败"（差 0.01 秒）
- **症状**：10 分钟完整录完，所有包都到了接收端，板子最后的对账却不一致，主动放弃提交。
- **根因**：用"会话代际号"丢弃上一场的残留音频帧时，读代际号的时机早于阻塞等待，导致**新一场的第一帧（10 ms）被误当成旧数据丢掉**。
- **解法**：在拿到一帧之后、处理之前再判断代际号。保留严格对账：采集样本数 = 编码样本数，确认的包数 = ceil(样本数 / 960)，任何一项不符都判失败，不提交。
- **验证**：对账失败要有明确的错误码；建议写一个原生单元测试，模拟"会话切换后第一帧"。

### 坑 5：60 分钟的录音太大，服务不收
- **症状**：一小时 WAV 约 115 MB，超过上传入口的 64 MB 限制。
- **解法**：接收端存档 WAV；WAV ≤ 32 MiB（约 17 分钟）时直接交 WAV，更长的用 ffmpeg 转成 AAC-LC 48 kbit/s 的 m4a（一小时约 22 MB），并用 ffprobe 校验编码、采样率和时长。
- **验证**：60 分钟合成测试，m4a 时长误差 ≤ 0.25 秒。

### 坑 6：录音越长，"结束"请求越容易超时
- **症状**：一小时录音结束时，板子报"结束请求失败"，但接收端其实已经保存了。
- **根因**：接收端在结束请求里**同步**解码 60 分钟音频（约 1.4 秒），超过了板子的请求超时。
- **解法**：结束请求只做校验（块数、字节数、SHA-256、包数、样本范围），通过后立刻回复"处理中"，解码、转码、交接放到后台线程。板子随后每 2 秒查询一次状态。
- **验证**：结束请求的耗时应在几百毫秒以内，和录音长度无关。

### 坑 7：家里 Wi-Fi 停顿好几分钟，缓冲被撑爆
- **症状**：一小时录音在第 24 分钟（另一次在第 6 分钟）中断，报"缓冲已满"。
- **根因**：上行**近乎停顿 5～6 分钟**（小请求还能通，大块一直传不完），而 1 MB 缓冲只能撑约 4 分钟；积压时每块接近 64 KB，每次写操作的超时只有 1.2 秒，失败就整块重来。
- **解法**（四件事一起做）：
  1. PSRAM 环形缓冲扩到 3 MiB（约 13 分钟）；
  2. 新块大小上限 16 KB，失败后减半（最低 4 KB），成功后翻倍恢复。**同一块的重试必须原样重发**，接收端靠"同序号 + 同内容"去重；
  3. 数据块的写超时从 1.2 秒改为 3 秒，控制类请求（开始、结束、状态）改为 5 秒；
  4. 单块重试窗口改为 600 秒，接收端"无数据超时"同步改为 630 秒（必须大于设备的重试窗口），整场墙钟上限 5400 秒。
- **验证**：写一个传输模型（真实 Opus 包 + 真实接收端 + 可加速的时间），复现"6 分钟近乎停顿"：旧参数必须失败，新参数必须成功。

### 坑 8：会话结束几秒后随机崩溃（Cache error）
- **症状**：录音中止约 4 秒后，Guru Meditation（Cache error）重启。回溯：一个核在协处理器（FPU）上下文切换，另一个核在跑唤醒词。
- **根因（推断，有依据）**：FreeRTOS 把每个任务的 FPU/PIE 寄存器保存区放在**该任务自己的栈上**。Opus 编码任务的栈放在 PSRAM 里，而且会用到 FPU/PIE 指令。其他任务触发惰性上下文切换时，如果 cache 正好被禁用（例如在写 flash），往 PSRAM 写这个保存区就会触发 Cache error。ESP-IDF 也明确要求：PSRAM 栈只能用于"cache 禁用时绝不会访问该栈"的任务。
- **解法**：编码任务**只在会话期间存在**。会话结束后先让它在不持锁的地方挂起，再用 `vTaskDeleteWithCaps` 删除，删除时会释放协处理器所有权。下一次开始时重新创建。
- **通用规则**：**会用到 FPU/PIE 的任务，栈不要放 PSRAM**；实在放不进内部 RAM，就尽量缩短它的生命周期。注意 lwIP、esp_http_client、cJSON 解析数字等路径里都有 FPU/PIE 指令。

### 坑 9：空闲后第一次开始就失败
- **症状**：开始录音时连接超时，会话直接作废。
- **根因**："开始"请求只尝试一次，而设备空闲后的第一次连接偶尔超过 1.2 秒。
- **解法**："开始"请求在 15 秒内重试（接收端对同一会话 ID 的开始请求是幂等的）。开始成功之前不采音，所以重试不会丢音频。

### 坑 10：语音对话之后，开不了录音（TaskCreate 失败）
- **症状**：先和小智聊过天，再说"开始记录会议"，立刻失败。
- **根因**：上传任务每次开始时现分配 8 KB 的内部栈。语音对话之后内部内存被打散，最大连续块只剩约 7 KB。
- **解法**：开机激活完成后（这时开机 HTTPS 已经结束，内存还是完整的）就把上传任务建好，常驻复用，每场会话用通知唤醒。**不要**改成编译期静态栈：那样开机做 HTTPS 时也少了 8 KB。

### 坑 11：别用堆任务跟踪做线上诊断
- **症状**：开启 `CONFIG_HEAP_TASK_TRACKING` 想查谁占了内存，结果板子开机就看门狗超时、反复重启。
- **根因**：开启后每次 free 都要拿互斥锁，esp_timer 回调和 Wi-Fi 省电路径里不能这样做；它本身还要额外占约 8 KB 内部内存。
- **解法**：线上只看 `heap_caps` 的空闲量、历史低水位和最大连续块，每 10 秒打印一次。

### 坑 12：弱信号时内部 RAM 几乎见底（**未完全解决**）
- **现象**：RSSI 约 −80 dBm、连续失败时，内部 RAM 低水位能降到几百字节（没有崩溃，录音也完整）。
- **已排除**：失败连接改为 RST 立即释放（`SO_LINGER {1,0}`），**没有明显效果**。
- **怀疑**：Wi-Fi 驱动的动态发送缓冲（默认 32 个，每个约 1.6 KB，都在内部 RAM）。注意：在 IDF 5.5 中打开 `SPIRAM_TRY_ALLOCATE_WIFI_LWIP` 会**强制改用常驻内部内存的静态发送缓冲**，不能盲目打开。
- **当前建议**：板子尽量靠近路由器（−70 dBm 以上）。

### 坑 13：换个地方，板子找不到接收端
- **症状**：在家正常，到公司一直"正在连接接收端"，然后报错。
- **根因**：接收端的 IP 地址写死在固件里。
- **解法**：每次开录前，板子在当前局域网**广播**一次 UDP 查询 `XZMEET/1 Q <32 位十六进制随机数>`（端口 8768）。接收端只回应局域网地址，回复内容为 `XZMEET/1 A <端口> <HMAC-SHA256(设备密钥, "XZMEET/1|随机数|端口")>`。板子验证 HMAC 通过才使用这个地址。**密钥不在网络上传输，同一局域网里的设备也无法冒充接收端。**找不到时，退回到上次找到的地址，再退回到固件里的配置地址。
- **注意**：板子和接收端必须在同一个网段；有些办公网络开启了客户端隔离，广播过不去。

### 坑 14：接收端电脑开着 VPN，默认路由不在局域网网卡上
- **根因**：macOS 的默认路由可能是 `utun` 隧道，不能用"默认网卡的 IP"作为监听地址。
- **解法**：监听所有网卡，但每个请求必须来自局域网或本机地址，并且 Host 头必须正好等于这条连接的本机局域网 IP:端口（防 DNS rebinding）。

### 坑 15：语音结束命令不好用
- **症状**：说"你好小智"后停顿，小智回一句"你叫我干嘛"；再说"结束会议记录"，它回"会议记录正在进行中"，并没有停。
- **根因**：(a) ASR 会把"小智"识别成"小志""晓智"，或者带上"呀"之类，严格相等的判断失败，这句话就被交给了大模型；(b) 大模型回复结束后，本地的命令窗口被关掉，下一句又被当成闲聊。
- **解法**：
  1. 录音期间，唤醒词由**本地**唤醒引擎检测，检测到后才打开一个 15 秒的命令窗口；窗口外的声音根本不送去识别，所以会议里有人说"结束会议"不会误停；
  2. 命令窗口里，**只认唤醒后的第一句话**：是结束命令就停，不是就关闭窗口，大模型也不回话；只有唤醒词（及其变体）不算第一句；
  3. 匹配方式是**整句匹配**：去掉唤醒词变体、开场词（请/帮我/好了/那就…）和句尾语气词（吧/了/啊/一下…）之后，剩下的部分必须正好是结束说法之一；以否定词开头、转述、疑问都不算；
  4. 每句识别结果都写进日志（原话 + 判断结果），方便调优。
- **验证**：原生单元测试覆盖 10 种唤醒变体、15 种结束说法、10 种不该停的说法。

### 坑 16：打印一行日志，板子就重启了
- **根因**：xiaozhi / ESP-IDF 默认用 newlib **nano printf**（`CONFIG_NEWLIB_NANO_FORMAT=y`），**不支持 `%lld` / `%llu`**，参数错位后 `%s` 读到非法地址，触发 LoadProhibited。
- **解法**：日志里的 64 位整数先转成 `long`，再用 `%ld` 打印。

### 坑 17：会议结束后一直停在结果界面
- **解法**：在结果界面上单击按键只返回主界面（不要顺带开启对话）；说唤醒词也返回；结果界面 10 分钟后自动返回（留足扫码时间）。

### 坑 18：一打开串口监视，板子就重启
- **根因**：USB-Serial/JTAG 打开时会触发一次软复位（rst:0x15）。
- **对策**：先开串口、再开始测试；把这次复位算进计划里，并提前告诉操作的人。

### 坑 19：开机反复"检查新版本失败"
- **现象**：错误码 32774（0x8006 = `ESP_ERR_ESP_TLS_CONNECTION_TIMEOUT`），连不上 OTA 服务器。
- **根因**：网络问题（DNS、代理、服务器），与录音固件无关。**不要误判成内存问题。**我们就误判过一次。
- **对策**：等它自动重试；检查路由器或代理；开发机走代理时，解析结果和板子不同（例如开发机解析到 198.18.x.x 这样的代理虚拟地址）。

### 坑 20：自己加的保护，最后变成了限制
- **现象**：开发期为了防止误提交，在接收端加了"累计最多处理 N 次"的上限，正式使用时成了障碍。
- **建议**：保护做成开关，默认设为"无限制"；真正要保留的是**防重复提交**（同一文件 SHA-256 去重、提交意图先落盘、结果未知时禁止自动重发）。

### 坑 21：转写服务没有"上传音频"的开放接口
- **我们的做法**：接收端用一个专用的 Chrome 实例（Playwright 控制，用户扫码登录一次），在服务的官方网页里，调用网页**自带的上传流程**完成上传和生成；之后用服务**官方开放平台 API** 读回笔记、生成不含原音的分享链接。
- **风险**：网页改版就可能失效；请遵守服务的用户协议；有官方上传接口时，应该优先用官方接口。
- **原则**：程序不导出、不保存账号令牌，令牌只留在那个浏览器里。

### 坑 22：刷机要安全
- 只写应用分区（我们的是 `[0x20000, 镜像末尾按 4 KB 对齐)`）；写之前保存应用区和前后相邻区域的快照，写完回读，逐字节比对；分区表、assets、bootloader 不动。
- 应用分区有两个（ota_0 / ota_1）时，可以把另一个固件放进 ota_1，通过 otadata 切换，**不覆盖**当前在用的固件。

## 6. 板子与接收端的协议

所有请求都带 `Authorization: Bearer <设备密钥>`，Host 必须是接收端的局域网 IP:端口。

| 请求 | 作用 | 要点 |
|---|---|---|
| `POST /v2/start/<会话ID>` | 开始 | 同一会话 ID 重复开始是幂等的 |
| `POST /v2/chunk/<会话ID>/<序号>` | 上传一块 | 内容为 `[u16 长度][Opus 包]…`；**落盘之后**才回确认；同序号同内容视为重复，同序号不同内容拒绝；回复 `next` |
| `POST /v2/finish/<会话ID>` | 结束 | 内容 `{count, bytes, sha256, packets, samples}`；校验通过后立刻回复 `processing`，后台解码 |
| `POST /v2/status/<会话ID>` | 查询 | `recording / processing / saved / complete(+url) / error` |
| `POST /v2/abort/<会话ID>` | 放弃 | 附带首个错误的诊断快照 |

**对账规则**（接收端）：块数、字节数、SHA-256、包数都一致，并且 `(包数−1)×960 < samples ≤ 包数×960`；逐包解码每包必须得到 960 个样本，最后截掉末包的补零部分。

## 7. 测试方法（按这个顺序来）

1. **原生单元测试**（在电脑上编译运行，不需要板子）：录音上限边界、环形缓冲回绕、上传策略、诊断事件环、自动发现报文解析、语音命令分类。
2. **接收端单元测试**：完整流程、重复与冲突、畸形包、各类对账失败、超时、60 分钟合成数据（7,500 块），以及 m4a 交接和压缩失败的处理。
3. **传输模型**：真实 Opus 包 + 真实接收端 + 可加速的时间（例如 20 倍速，60 分钟约 3 分钟跑完），用来复现链路变慢、断网、近乎停顿等场景。**旧版本必须能复现真实的失败**，新版本才算可信。
4. **真机阶梯**：3 分钟 → 10 分钟 → 60 分钟（只保存，不提交）→ 60 分钟完整产品流程。每次都采集串口日志（内存低水位、RSSI、每次请求的耗时），录完人工听一遍。
5. **信号位置**：分别在靠近路由器（−50 dBm 左右）和信号差的位置（−80 dBm 左右）各测一次。
6. **语音命令**：停顿后再说、带语气词的说法、否定说法、ASR 识别出变体的情况。

## 8. 还没解决或没测过的

- 弱信号下内部 RAM 低谷（坑 12）；
- 真实 3～5 人会议的收音距离和转写质量；
- 长时间无人值守的稳定性；
- 依赖网页上传流程（坑 21）带来的脆弱性。
